# vellum

Repository-specific decisions; packaging and release rules follow `/code/pacman/RELEASE_POLICY.md`, with build details in `RELEASES.md`.

## Test builds update themselves; releases do not

vellum has two ways out. GitHub Releases are for anyone and carry no updater: a release build has no build name, so it never looks for updates. Test builds are for testing with the author: `tools/publish-update` builds the current commit for Windows, names the build after it, and publishes it to the update server at `http://updates.waka.mx/vellum/` (on the Hetzner machine, `/srv/vellum-updates`, served by `/etc/nginx/sites-available/updates-waka.conf`), where a test copy whose user said yes fetches it within a minute. A test build asks once, on its first run, and does not look until the answer is yes; its title says it is a test build, with its commit, and Ctrl+U turns updating off and on. It restarts into a new build once it has been left alone for two minutes with nothing unsaved, with no wait between restarts, as gtube does: each window comes back with its file, scroll, zoom and editor, so taking every commit costs the user nothing. A build that keeps failing on start goes back to the one before (gesso's `gs_update`). First installs come from `https://updates.waka.mx/vellum/index.html`, with `vellum-test-windows.zip`; the public README links releases only. Agents run `tools/publish-update` themselves after each commit worth testing, without asking, as on the other apps built on gesso; it refuses a tree with uncommitted changes. The signing key is `~/.config/vellum/update-signing.key` on the author's machine and never goes into the repository or CI.
